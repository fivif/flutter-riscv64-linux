# 为什么不把源码放进仓库

有人会问：既然要做「完整的开源引擎仓库」，为什么不把源码一起放进去？

答案是：**引擎源码不是一个仓库，是 271 个仓库组成的依赖图。**
放进来在技术上、法律上、维护上都不成立。

---

## 一、体量

| 项 | 量级 |
|---|---|
| Flutter 引擎 `DEPS` 里 pin 的仓库数 | **271 个** |
| `DEPS` 文件本身 | 40 KB / 1016 行 |
| 完整 `gclient sync` 后 `engine/src` | 约 **2 GB** |
| 单个最大依赖（skia） | 400 MB+ |
| 完整 git 历史（含各仓库） | 5–8 GB |

主力依赖包括（每个都是独立仓库、独立许可证、独立维护者）：

```
flutter          skia             dart              angle
icu              harfbuzz         libcxx            abseil-cpp
flatbuffers      vulkan-deps      swiftshader       llvm
libpng           libjpeg-turbo    zlib              freetype2
boringssl        perfetto         webkit_inspection_protocol
...（共 271 项）
```

---

## 二、GitHub 硬限制

| 限制 | 数值 |
|---|---|
| 单文件上限 | **100 MB**（硬拒绝） |
| 推荐仓库体积 | < 1 GB |
| 警告阈值 | > 5 GB |
| LFS 免费额度 | 1 GB 存储 / 1 GB 月流量 |

引擎的 `deps` 里有多个超过 100 MB 的文件（预编译 dart-sdk、测试资源、字体）。

**就算用 LFS，1 GB 免费额度也不够装 2 GB 源码。**

---

## 三、许可证（这条最要命）

引擎的组件**不是同一份许可证**：

| 组件 | 许可证 |
|---|---|
| Flutter / Skia | BSD-3-Clause |
| Dart | BSD-3-Clause |
| ICU | Unicode License |
| HarfBuzz | MIT |
| libcxx / LLVM | Apache-2.0 WITH LLVM-exception |
| Abseil | Apache-2.0 |
| freetype | FreeType License (FTL) / GPLv2 双许可 |
| zlib | zlib License |
| BoringSSL | OpenSSL + ISC 混合 |

把源码复制进我们的仓库，等于**我们在分发这些组件**。那就必须：

1. 逐仓库保留完整 LICENSE 与版权声明
2. 声明每个组件的确切来源、版本
3. 处理 `DEPS` 里那些 `custom_vars` 覆盖的、许可证不清的组件
4. 对 GPL 双许可的组件（如 freetype）做合规判断

**这不是「顺手放一下」能解决的。做错了仓库会被 DMCA takedown。**

---

## 四、维护上会变成陷阱

`DEPS` 的语义是「按 revision 精确拉取」：

```python
'engine/src/flutter/third_party/skia':
   Var('skia_git') + '/skia.git' + '@' + Var('skia_revision'),
```

**源码快照一旦进仓库，立刻与 `DEPS` 脱节。** 后果：

- 用户拿到的源码是「某个时间点的」，但 `DEPS` 说要用另一个 revision → 构建混乱
- 上游每周更新 → 我们的快照永远落后
- 用户以为快照是「正确版本」→ 构建失败 → 报 issue 给我们
- 我们要么永远追上游，要么仓库变成陷阱

---

## 五、正确做法：锁 revision，不锁文件

这就是 `pinned/` 目录的作用。用 **40 KB 的文本** 替代 **2 GB 代码**：

```
pinned/
  DEPS                 271 个依赖的 revision 清单（40 KB）
  .gclient             gclient 配置
  flutter.version      framework + engine revision
  dart.VERSION         Dart 3.15.0-51.0.dev
  sdk-hashes.txt       产物 sha256
```

用户执行：

```bash
gclient sync -r 57d5122cd9dcfd0174ba963e61df20a328378c64
```

拿到的是**官方原版源码**，revision 精确一致，许可证由 Google 与各上游负责。

---

## 六、那「完整」体现在哪

本仓库的「完整」不是指「包含源码」，而是指：

| 维度 | 完整程度 |
|---|---|
| 构建脚本 | ✅ 环境检查 → gn gen → 引擎 → SDK → frontend_server → 安装 → 核验 |
| args 配置 | ✅ 双模式实测可用 |
| clang shim | ✅ 两个必需补丁（rtlib 冲突、LTO 走 lld） |
| 补丁 | ✅ Skia 字体族匹配（+59/−2，5.6× 加速） |
| 版本锁定 | ✅ 271 个依赖的 revision + 产物 sha256 |
| 踩坑记录 | ✅ 16 条，症状 → 根因 → 修法 |
| 实测数据 | ✅ 构建耗时、体积、性能基准、测量陷阱 |
| 可用产物 | ✅ GitHub Release（60 MB，解压即用） |

**「能按文档复现」比「把源码塞进来」有价值得多。**

---

## 七、如果你真的需要离线源码包

可以自己打，但不建议进公开仓库：

```bash
# 在自己机器上
gclient sync -r 57d5122cd9dcfd0174ba963e61df20a328378c64
tar cfz flutter-engine-src.tar.gz engine/src \
  --exclude='.git' --exclude='out'
# 约 1.5~2 GB
```

存到自己控制的存储（内网、对象存储），**不要提交进 git**。

如果确实要公开分发，正确途径是尊重各上游仓库的 `git clone` —— 那就是
`DEPS` + `gclient sync` 做的事。
