# 并发构建的代价：把 sshd 压死

这条是实测踩出来的，不是理论。

---

## 症状

构建跑着跑着，SSH 全部超时：

```
ssh: Connection timed out during banner exchange
```

但：

| 检查 | 结果 |
|---|---|
| `ping 10.5.90.75` | ✅ 4~5 ms，网络正常 |
| TCP 22 | **开放**（sshd 在监听） |
| TCP 53317（应用服务） | **开放**（用户态进程还活着） |
| SSH 登录 | ❌ 超时 20 分钟以上 |

**判断方法**：ping 通、端口通、但 SSH 不握手 → **不是网络问题，是主机负载/内存问题**。
sshd 进程在，但 fork 不出子进程来服务新连接。

---

## 根因

同时跑了三个 ninja：

1. 干净引擎构建（4490 步）
2. 应用构建（`flutter build linux`）
3. Dart SDK 子集（916 步）+ 快照（497 步）

`/proc/loadavg` 冲到 **19+**（16 核），7.7 GiB 内存被多个 clang 吃满。

clang 编译大文件时单个进程可以吃到 1~2 GB。ninja 默认按核数并行（16），
峰值内存需求远超物理内存，于是大量 swap，整个系统进入 thrashing。

---

## 规则

### 1. 同一时间只跑一个 ninja

```bash
pgrep -a ninja     # 启动前必查
```

同一个 `out/` 目录跑两个 ninja 会**互相破坏**；不同 `out/` 目录虽然文件不冲突，
但**争抢 CPU 和内存**，一样会把机器压死。

### 2. 别用默认并行度跑大项目

```bash
# 按内存而不是核数决定并行度
ninja -j 8          # 7.7 GiB 内存的建议值
# 或
ninja -j 6
```

16 核全开在编译期内存峰值下是自杀。

### 3. 长任务用 setsid，但别同时开多个

```bash
setsid nohup ninja -j 8 ... > build.log 2>&1 < /dev/null &
```

---

## 如果已经被压死了

**没有 SSH 就没有远程手段。** 能做的只有等：

- 构建自己跑完，负载下降，sshd 恢复
- 或者 OOM killer 杀掉 clang，负载下降，sshd 恢复

期间不要反复重试 SSH —— 每次重试都要 fork 一个 sshd 子进程，只会加重压力。

**等待策略**：每 45~60 秒试一次，`ConnectTimeout` 设 20~25 秒。

---

## 预防清单

- [ ] 构建前 `pgrep -a ninja` 确认没有别的在跑
- [ ] 用 `-j 8` 而不是默认 16
- [ ] 大构建（引擎/SDK/应用）串行排队，不要并行
- [ ] 关键节点先 `free -m` 看可用内存
- [ ] 板子上同时跑着的服务（比如被测试的应用）也会占内存，测之前先停
