同一显示环境（Xvfb 1280×800、llvmpipe 软件渲染）、
统一加 `dbus-run-session`，3 次取中位数。

## 三、Skia 字体族匹配补丁的效果

这是本项目性能价值最高的一项。

**补丁**：`patches/0001-fontconfig-hoist-pattern-sort.patch`（+59 / −2）
**位置**：`skia/src/ports/SkFontMgr_fontconfig.cpp`

**问题**：pattern 侧最多 272 个族名，在字体循环里被重复抽取、重复排序。

**测试应用**：LocalSend GUI（Flutter，冷启动到首帧）

| 配置 | 首帧耗时 | 相对 |
|---|---|---|
| 723 字体，无补丁 | **9043 ms** | 1.0× |
| 723 字体，有补丁 | **1616 ms** | **5.6×** |
| 56 字体，无补丁 | 3690 ms | 2.5× |
| 56 字体，有补丁 | **894 ms** | **10.1×** |

### 重要：补丁与减字体是替代关系，不是叠加

如果两者独立生效，56 字体 + 补丁应该是 `1616 × (894/3690) ≈ 390 ms`。
实测是 **894 ms**，与「56 字体无补丁」的 3690 ms 相比只有 4.1×，
和「723 字体有补丁」的 5.6× 同一量级。

**结论：两者解决的是同一个瓶颈，不能叠加。** 这个反直觉的结果值得记住 ——
不要用「分别优化再相乘」来预测。

### 为什么这个补丁值得上游化

723 个字体是 **Bianbu 的默认配置**，不是我们硬塞的。
板上任何 GTK4 / libadwaita / Chromium 程序都在付这笔钱。

## 四、AOT（release）的真实收益

同一个应用，debug（JIT）vs release（AOT）：

| 配置 | 首帧 | 说明 |
|---|---|---|
| debug，无补丁，723 字体 | 9043 ms | 字体瓶颈掩盖了一切 |
| release，无补丁，723 字体 | ~5093 ms | 只快 1.8× |
| debug，有补丁，723 字体 | 4670 ms | 只快 1.9× |
| **release，有补丁，723 字体** | **1616 ms** | **5.6×** |

**AOT 的收益被字体瓶颈掩盖了。** 单独看 release 只有 1.8×，
单独看补丁只有 1.9×，两者一起才有 5.6×。

这是「优化要打在最痛的地方」的一个具体案例。

## 五、D-Bus 的 25 秒陷阱（测量前必读）

Flutter Linux 应用在没有 D-Bus session 时，`activate` 会卡
**25,000 ms**（libdbus 默认超时），而且是**两处**，合计 50 秒。

**打任何 profiler 都看不出来** —— 它表现为「启动很慢」，不是 CPU 热点。

我们最初测到的 58.9 秒里，有 50 秒是假的。

### 自查

```bash
dbus-run-session -- ./your_app 2>&1 | grep "EVENT: activate"
```

`activate` 应该在 **200~400 ms**。如果是 25000，说明忘了 `dbus-run-session`。

我们有一整批数据（六次运行）因为这个原因作废。

## 六、GPU 相关的实测（供参考）

板上 GPU 是 PowerVR Rogue（BVNC 36.56.104.183），驱动和固件状态都是 OK 的。

GLES 基准（`glFinish` 后计时）：

| 测试 | PowerVR | llvmpipe（软件） |
|---|---|---|
| 填充率 | 1420.9 fps | 1614.2 fps |
| 5000 三角形 | **137.9 fps** | 41.1 fps |

填充率软件反而快 14%（TBDR 的 tile 开销），几何负载 GPU 快 3.35×。

**但 Xvfb 不支持 DRI3**，所以 zink 建不了 swapchain：

```
vulkan: No DRI3 support detected - required for presentation
MESA: error: zink: could not create swapchain
```

结论：**GPU 硬件没问题，是测试环境的显示后端不支持。**
上真实 Xorg/Wayland 才能验证 GPU 呈现路径。
